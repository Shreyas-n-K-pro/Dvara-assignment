What Real-World Problem Does This Service Solve?

Traditional basic web applications store a simple column like current_balance = 5000 in a user or loan table. Whenever a repayment occurs, they run UPDATE loans SET current_balance = current_balance - 500. In real banking, this leads to catastrophic problems:

1. The "Ghost Balance" Problem

If a network glitch or partial crash occurs during a payment, the balance table might update but the audit history fails, or vice-versa. You have no mathematical proof where the money came from or went.

2. Floating-Point Rounding Leakage

JavaScript 0.1 + 0.2 = 0.30000000000000004. Over 100,000 micro-installments, fractions of a paisa accumulate into significant discrepancies that fail regulatory RBI banking audits.

3. Double-Dipping Race Conditions

A borrower with ₹10,000 outstanding clicks "Pay ₹7,000" in two browser tabs simultaneously. Without database-level row locking, both threads read ₹10,000, both succeed, and the borrower pays ₹14,000, creating negative principal.

How Our Implementation Solves It

We use Double-Entry Ledger accounting where balances are derived, pessimistic row locking (SELECT FOR UPDATE), BigInt paise, and SHA-256 idempotency. The ledger trial balance proves net zero difference across every transaction.

3.2 Loan Calculation Engine & Pure Integer Math

Zero Float Drift

The system implements pure integer BigInt arithmetic representing all money in paise (1 Rupee = 100 paise). Floating-point types (number or FLOAT) are strictly prohibited in the core financial paths to prevent IEEE-754 decimal rounding leakage.

1. Flat Rate Formula

Interest is computed upfront on the entire initial principal regardless of tenure progression.

totalInterest = divRoundHalfUp(P * rateBps * months, 10000n * 12n)
instalmentInterest = divRoundHalfUp(totalInterest, months)
instalmentPrincipal = divRoundHalfUp(P, months)

2. Reducing Balance EMI Formula

Interest is recalculated each cycle strictly on remaining outstanding principal.

monthlyRate = rateBps / (10000 * 12)
EMI = P * [r * (1 + r)^n] / [(1 + r)^n - 1]
interest_i = divRoundHalfUp(balance_i * rateBps, 10000n * 12n)
principal_i = EMI - interest_i
divRoundHalfUp: Integer Half-Up Rounding Algorithm src/utils/math.ts 
export function divRoundHalfUp(numerator: bigint, denominator: bigint): bigint {
  if (denominator === 0n) throw new Error("Division by zero");
  // Formula: floor((2 * numerator + denominator) / (2 * denominator))
  // Exactly implements commercial banker's half-up rounding in pure BigInt integer domain
  return (2n * numerator + denominator) / (2n * denominator);
}

export function canonicalize(obj: any): string {
  if (obj === null || typeof obj !== "object") {
    return typeof obj === "bigint" ? obj.toString() : JSON.stringify(obj);
  }
  if (Array.isArray(obj)) {
    return "[" + obj.map(canonicalize).join(",") + "]";
  }
  const keys = Object.keys(obj).sort();
  const pairs = keys.map((k) => `${JSON.stringify(k)}:${canonicalize(obj[k])}`);
  return "{" + pairs.join(",") + "}";
}

export function computeRequestHash(body: any): string {
  const canonical = canonicalize(body);
  return crypto.createHash("sha256").update(canonical).digest("hex");
}

3.5 Concurrency Control & Row-Level Locking

Race-Condition Immune

When two repayments for the same loan arrive at the exact same millisecond across different worker processes or CPU threads, they would both read the same outstanding balance, allocate principal concurrently, and drive the loan into an illegal negative balance.

Why Optimistic Locking Was Insufficient

Optimistic locking relies on a version counter (WHERE version = 1). If two legitimate payments of ₹5,000 arrive for a ₹15,000 balance, the second thread would throw a version conflict and fail outright, forcing client retries. In high-traffic batch ingestion, optimistic locking causes 30%+ spurious failure rates.

Our Solution: Pessimistic Row Locking (SELECT FOR UPDATE)

Inside Prisma's prisma.$transaction({ isolationLevel: 'ReadCommitted' }), we immediately execute:

await tx.$queryRaw`SELECT id, status FROM loans WHERE id = ${loanId} FOR UPDATE`;

This places an exclusive write lock on the loan row at the MySQL InnoDB engine level. Thread 2 is held in queue until Thread 1 completes, posts ledger entries, and commits. When Thread 2 unblocks, it reads the freshly updated derived balance, safely allocating against the remaining balance.

Deadlock Resilience with Exponential Jittered Backoff src/modules/repayments/repayment.service.ts 
let attempts = 0;
while (attempts < MAX_RETRIES) {
  try {
    return await prisma.$transaction(async (tx) => {
      // 1. Pessimistic Lock
      await tx.$queryRaw`SELECT id FROM loans WHERE id = ${loanId} FOR UPDATE`;
      // 2. Fetch fresh derived balance & overdue schedules
      // 3. Waterfall allocation & ledger posting
    }, { timeout: 10000 });
  } catch (error: any) {
    if ((error.code === 'P2034' || error.message?.includes('Deadlock')) && attempts < MAX_RETRIES - 1) {
      attempts++;
      const jitter = Math.floor(Math.random() * 50);
      await sleep(100 * Math.pow(2, attempts) + jitter);
      continue;
    }
    throw error;
  }
}

Q6 Why is there no 'current_balance' column in the loans table?

Q11 What is the difference between Flat Rate and Reducing Balance interest?

Q12 How does your integer half-up rounding algorithm work?
Calculations ▼
🗣️ Speak Naturally

"In pure integer division \( n / d \), truncation discards decimals. To achieve exact mathematical half-up rounding (where 0.5 rounds up to 1), we use the algebraic formula: (2 * n + d) / (2 * d). By multiplying both the numerator and denominator by 2 and adding the denominator to the numerator, integer truncation yields the exact half-up rounded result without converting to float."

Technical Deep Dive

Example: Round \( 7 / 2 = 3.5 \). Formula: (2*7 + 2) / (2*2) = (14 + 2) / 4 = 16 / 4 = 4 (correctly rounded up). Round \( 6 / 4 = 1.5 \): (2*6 + 4) / (2*4) = 16 / 8 = 2. Round \( 5 / 4 = 1.25 \): (2*5 + 4) / 8 = 14 / 8 = 1. Completely integer-based.

Technical Deep Dive

In src/modules/schedules/calculator.ts: at instalmentNumber === tenureMonths, we bypass the standard calculated principal and assign the exact remaining balance. This prevents orphan 1-paisa balances from keeping loans artificially open.

Category 5: Idempotency & Network Safety

Q21 Why is idempotency essential in payment systems?
Idempotency ▼
🗣️ Speak Naturally

"On mobile networks, timeouts frequently occur: the server processes the payment successfully, but the TCP connection drops before the 201 response reaches the client. The client or payment gateway automatically retries the request. Without idempotency, the server would process the payment a second time, debiting the customer twice. Idempotency guarantees that executing the same operation multiple times yields the exact same result as executing it once."

Technical Deep Dive

Tested in our synthetic dataset: 500 retry requests with identical keys were replayed against the server. Exactly 0 double-postings occurred; all 500 received the cached HTTP 200 response without triggering any database mutations.

Q22 How do you handle key reuse with a different payload?
Idempotency ▼
🗣️ Speak Naturally

"We compute a SHA-256 hash of the incoming request body and store it alongside the idempotency key. When a request arrives with an existing key, we compare its hash with the stored hash. If the hashes match, it is an identical retry, and we return the cached response with HTTP 200. If the hashes differ, it means the client reused a key for a different payment amount or loan, and we immediately reject it with HTTP 409 Conflict."

Technical Deep Dive

HTTP 409 response payload: { success: false, error: { code: 'CONFLICT', message: 'Idempotency key reused with different payload' } }. This was tested with 50 intentional conflict events in our dataset, all correctly returning 409.

Q23 Why is canonical JSON serialization necessary before hashing?
Idempotency ▼
🗣️ Speak Naturally

"Standard JSON serialization does not guarantee key ordering. For example, {'loanId':'1','amount':100} and {'amount':100,'loanId':'1'} are semantically identical payloads, but produce completely different SHA-256 hashes with naive string hashing. Our canonicalize() function recursively sorts all object keys alphabetically, guaranteeing that semantically identical JSON objects always produce the exact same cryptographic hash."

Technical Deep Dive

In addition to recursive key sorting, canonicalize() converts native BigInt values to string representation (e.g. 5000n → "5000"), preventing JavaScript runtime type errors during serialization.

Q24 Where in the request lifecycle is the idempotency key saved?
Idempotency ▼
🗣️ Speak Naturally

"The idempotency key is saved inside the same database transaction as the repayment allocation and ledger entries. This guarantees that the key is only persisted if the entire payment succeeds. If the payment fails or rolls back, the key is rolled back as well, allowing the client to fix the issue and retry cleanly."

Technical Deep Dive

If you save the idempotency key in Redis or database before executing the business logic, a server crash mid-payment would leave a 'poisoned' key in the database that blocks future legitimate retries with a false cached response.

Category 6: Concurrency Control & Row Locking

Q26 How does SELECT FOR UPDATE prevent race conditions during repayment?
Concurrency ▼
🗣️ Speak Naturally

"When a repayment begins, we execute SELECT id FROM loans WHERE id = ? FOR UPDATE inside a transaction. This instructs MySQL InnoDB to place an exclusive write lock on that specific loan row. Any other concurrent payment for the same loan is forced to wait in queue. When the first payment commits, the second payment proceeds and recalculates the remaining balance against fresh ledger state, preventing double-allocation."

Technical Deep Dive

MySQL InnoDB row locks are held until COMMIT or ROLLBACK. With READ COMMITTED isolation level, once Thread 1 commits, Thread 2's subsequent SELECT reads only committed data, ensuring accurate derived balance calculation.

Q27 What is a deadlock and how does your application recover from one?
Concurrency ▼
🗣️ Speak Naturally

"A deadlock occurs when Transaction A holds a lock on Row 1 and requests Row 2, while Transaction B holds a lock on Row 2 and requests Row 1, creating a circular dependency. MySQL automatically detects deadlocks and kills one transaction with error 1213. We wrapped our transaction in an automatic retry wrapper with randomized exponential backoff (retrying up to 3 times), allowing transient deadlocks to self-heal without failing the user."

Technical Deep Dive

Retry logic: catches Prisma error code P2034 (transaction conflict) or error message containing 'Deadlock'. Formula: delay = 100 * 2^attempt + random(0, 50) ms. The randomized jitter prevents contending threads from retrying at the exact same microsecond.

Q28 Why did you choose pessimistic locking over optimistic locking?
Concurrency ▼
🗣️ Speak Naturally

"Optimistic locking (version checking) is designed for read-heavy workloads where concurrent writes are rare. In high-traffic financial payment processing or batch ingestion, multiple webhooks can hit the same loan simultaneously. Under optimistic locking, all but one transaction would fail with version conflicts, causing massive client-side retry storms. Pessimistic row locking queues the transactions cleanly, allowing both payments to succeed sequentially."

Technical Deep Dive

Benchmarked during our 5,000-event replay across 8 concurrent workers: with pessimistic locking, 179.4 req/s were achieved with zero application-level transaction aborts and zero 500 errors.

Q29 What database isolation level is configured and why?

🗣️ Speak Naturally

"We use READ COMMITTED isolation level. MySQL's default is REPEATABLE READ, which uses next-key gap locks that can lock ranges of index records, dramatically increasing deadlock frequency during high-concurrency inserts. READ COMMITTED eliminates gap locking for simple statements while our explicit SELECT FOR UPDATE provides precise row-level exclusivity where needed."

Technical Deep Dive

In Prisma: prisma.$transaction(async (tx) => { ... }, { isolationLevel: 'ReadCommitted', timeout: 10000 }). Setting a 10-second timeout guarantees no runaway lock can hang MySQL worker threads indefinitely.

Q47How would you optimize balance queries when ledger entries reach 50 million rows?
System Design▼
🗣️ Speak Naturally

"Deriving balances by summing all historical rows becomes slow at 50M entries. The industry solution is Periodic Balance Checkpointing: at the end of each day or month, compute and store an immutable snapshot of the account balance as of that timestamp. A current balance query then only sums entries from the latest snapshot forward."

Query: Current Balance = CheckpointBalance(T_last) + SUM(Entries between T_last and NOW). This reduces the aggregation from 50M rows to a few dozen rows while preserving double-entry mathematical proof.

Q48Would you use Redis in this architecture and what are the trade-offs?
System Design▼
🗣️ Speak Naturally

"Redis is excellent for caching read-heavy, low-criticality data like JWT blocklists, rate limiting, and loan product definitions. However, I would never store financial balances or authoritative idempotency keys in Redis alone without database backing, because Redis is an in-memory store that can lose data during failover, violating strict financial ACID requirements."

A hybrid pattern: write idempotency key to Redis with a 24-hour TTL for sub-millisecond fast-path deduplication, backed by MySQL idempotency_keys table as the durable source of truth.

Q49How would you handle asynchronous webhook notifications for completed payments?
System Design▼
🗣️ Speak Naturally

"I would use the Transactional Outbox Pattern. Inside the repayment database transaction, insert an event record into an outbox_events table. A separate background worker (or Debezium CDC) reads uncommitted outbox events and publishes them to a Kafka or RabbitMQ topic, guaranteeing at-least-once delivery without distributed transactions."

Directly publishing to Kafka inside the HTTP request before database commit is an anti-pattern: if the database transaction rolls back, an invalid webhook notification would have already reached the customer.

8. 15 Real-World Scenarios & Edge Cases Section 8

Real-world production situations: what happens step-by-step in the code, what status code is returned, and how the database behaves.

Scenario 1: Concurrent Double-Payment on Same Loan

Concurrency

A borrower has an outstanding balance of ₹10,000. They open two tabs and click "Pay ₹6,000" at the exact same millisecond.

Step-by-Step System Execution:
1. Request 1 and Request 2 arrive on separate Node.js worker threads.
2. Request 1 enters prisma.$transaction and executes SELECT id FROM loans WHERE id = ? FOR UPDATE, acquiring an exclusive row lock.
3. Request 2 attempts the same lock and is blocked by the MySQL InnoDB engine.
4. Request 1 derives outstanding balance (₹10,000), allocates ₹6,000, updates schedule, posts ledger entries, commits, and releases the lock.
5. Request 2 unblocks, re-reads the fresh derived balance (now ₹4,000), sees that the requested ₹6,000 exceeds ₹4,000, and immediately aborts.
6. Request 1 returns HTTP 201 Created; Request 2 returns HTTP 400 Bad Request ("Payment exceeds balance").
💡 Interviewer insight: Emphasize that validating balance AFTER acquiring the lock is the crucial design detail that prevents double-allocation.

Scenario 2: Network Drops Mid-Repayment (Duplicate Retry)

Idempotency

A mobile payment gateway posts ₹1,000 with Idempotency-Key: pay-123. The server commits the payment, but the connection drops before the 201 response is received. The gateway automatically retries with the same key and payload.

Step-by-Step System Execution:
1. Retry request arrives with Idempotency-Key: pay-123.
2. Fast-path lookup finds pay-123 in idempotency_keys table.
3. Canonical SHA-256 hash of retry body matches the stored requestHash.
4. The service short-circuits execution: zero database locks acquired, zero ledger entries created, zero schedule mutations.
5. Returns HTTP 200 OK with the cached original response body and receipt details.

Scenario 3: Idempotency Key Reused with Different Payload

Idempotency

A buggy client sends a request with Idempotency-Key: pay-123 for ₹1,000, and then mistakenly reuses pay-123 for a different payment of ₹5,000.

Step-by-Step System Execution:
1. Server looks up pay-123 in idempotency_keys.
2. Computes SHA-256 of new payload (₹5,000) and compares against stored hash (₹1,000).
3. Hashes do not match → payload divergence detected.
4. Returns HTTP 409 Conflict: "Idempotency key reused with different payload". No mutations occur.

Scenario 4: Repayment Attempted on Non-Disbursed Loan

Lifecycle

A client attempts to post a repayment against a loan that is in APPLIED or APPROVED status before disbursement.

Step-by-Step System Execution:
1. Repayment service acquires lock on loan record.
2. Checks loan.status. Because status is not DISBURSED, throws ValidationError.
3. Returns HTTP 400 Bad Request: "Loan is not in DISBURSED status".

Scenario 5: Repayment Exceeds Total Outstanding Balance

Step-by-Step System Execution:

2. Total outstanding is determined to be exactly 350,000 paise (₹3,500).
3. 500,000 paise > 350,000 paise → rejects with HTTP 400 Bad Request: "Payment amount exceeds total outstanding balance".

9. System Design & Scalability Section 9

How to scale this financial engine to handle millions of borrowers, 10,000+ TPS, and multi-region deployment.

Production Scaling Blueprint

1. Horizontal Database Sharding

Shard MySQL databases by hash(borrowerId) % N or tenantId. Because loans are borrower-specific, all payments, schedules, and row locks for a given loan remain contained within a single shard, preserving local ACID transactions without distributed 2PC.

2. Read Replicas & CQRS

Route write operations (repayments, disbursements) to the Primary MySQL instance. Route read-heavy traffic (schedule viewing, borrower profiles, audit inspection) to Read Replicas, freeing the primary engine for high-concurrency row locking.

3. Periodic Balance Checkpointing

To prevent balance queries from scanning millions of ledger entries, introduce daily balance snapshots: Current Balance = SnapshotBalance(T_last) + SUM(Entries after T_last), keeping query execution sub-millisecond at 100M+ entries.

4. Transactional Outbox & Event Streaming

Write domain events to an outbox_events table inside the payment transaction. A Debezium CDC or background worker streams committed events to Apache Kafka for asynchronous downstream processing (SMS alerts, data lake, credit bureau reporting).

10. Honest Limitations & Real Code Quirks Section 10

Real, honest technical trade-offs and code quirks from the actual codebase. High-maturity interview gold.

What I Would Honestly Tell an Interviewer

Interviewers love candidates who can critique their own codebase with engineering honesty rather than pretending everything is perfect.

1. Read-Time Derived Balances at Massive Scale

Current Implementation: Balance is calculated on-the-fly by summing ledger entries inside the transaction.
Trade-Off: This guaranteed 100% mathematical consistency with zero balance drift across our 5,000 events. However, on a table with 50 million historical entries, calculating balance via full scan would introduce query latency. In a future iteration, I would implement monthly balance checkpointing tables.

2. Test Suite Parallel Execution Hangs (Node.js Orphans)

Current Implementation: Running all 11 test suites concurrently via Jest default parallel workers can occasionally cause MySQL connection pool exhaustion or socket hangs on Windows.
Resolution: Tests must be executed with --runInBand to run sequentially, ensuring clean database state isolation between suites.

3. Seed Script Legacy Role Discrepancy

Code Quirk: The original Prisma schema has legacy enum entries (ADMIN, OFFICER) alongside LOAN_OFFICER, MANAGER, and AUDITOR. While the seed script was aligned, legacy test suites may still reference old role names.

4. Single-Instance node-cron Limitation

Current Implementation: Midnight accrual is scheduled via node-cron inside the running Node process.
Limitation: If you scale out to 10 Docker containers behind a load balancer, all 10 containers would attempt to run the midnight cron. While our database unique constraint prevents double-posting, it creates unnecessary database contention. A production multi-pod setup requires a distributed job scheduler like BullMQ or Kubernetes CronJob.
