The Real-World Problem We Set Out to Solve

Most simple web applications handle money using a naive database column: UPDATE accounts SET balance = balance - 500. In financial microfinance, this causes three catastrophic problems:

⚠️ 1. Floating-Point Rounding Leakage

JavaScript and databases use IEEE-754 floats where 0.1 + 0.2 = 0.30000000000000004. Over 100,000 micro-loan repayments, fractions of a paisa drift, causing severe regulatory audit discrepancies.

⚠️ 2. The "Ghost Balance" Drift

If a balance column is stored separately from audit records, a partial crash or manual admin edit causes the stored balance to permanently diverge from transaction history with no mathematical proof.

⚠️ 3. Concurrent Double-Dipping Race

If a borrower owes ₹10,000 and hits "Pay ₹6,000" in two browser tabs at the same time, two concurrent threads read ₹10,000, both succeed, and the borrower pays ₹12,000, creating negative principal.

✅ How Our Architecture Eliminates All Three

We represent money strictly in pure integer BigInt paise (zero float error). We maintain zero stored balance columns (all balances are derived from an immutable double-entry ledger). And we wrap repayments in an atomic Prisma transaction with MySQL pessimistic row locking (SELECT FOR UPDATE), serializing concurrent payments and guaranteeing idempotency.

Connecting Each Point in the Flow

POINT 1

Who is Calling the System? (The Ingestion Layer)

Requests enter from three distinct sources at the top of the diagram:
  • Users / Postman: Human operators interacting via our REST API across 3 segregated roles (LOAN_OFFICER, MANAGER, and AUDITOR).
  • Daily cron: A node-cron scheduled job that fires automatically at midnight to trigger daily overdue interest and penalty accruals.
  • Replay engine: A multi-threaded test client running 8 concurrent workers replaying 5,000 synthetic events to benchmark real-world performance.
How to say this to the interviewer: "Requests originate from three places: external loan officers and managers via REST API, a background midnight cron for daily interest accruals, and an 8-worker replay harness we built to stress-test concurrent payments."
POINT 2

The Express API Gate: Security & Error Guardrails

Before touching any business logic, every HTTP request passes through three strict middleware filters:
  • JWT auth: Verifies the HMAC-SHA256 bearer token. Rejects invalid or expired credentials with HTTP 401 Unauthorized.
  • Role check: Enforces Segregation of Duties. For instance, loan officers cannot approve loans or inspect trial balances. Rejects unauthorized attempts with HTTP 403 Forbidden.
  • Error handler: Translates typed exceptions into clean RFC-compliant JSON responses (e.g., 400 for bad amounts, 404 for missing loans, 409 for idempotency payload conflicts).
How to say this to the interviewer: "Our API gate ensures zero unauthorized access. It checks JWT validity, enforces role-based access control, and sanitizes all errors so sensitive database traces never leak to the client."
POINT 3

The Domain Services (App Logic)

Once cleared, requests reach their dedicated business service:
  • Loans + schedules: Computes flat-rate or reducing-balance EMI amortization schedules using exact integer math in paise.
  • Repayments: Orchestrates the waterfall payment allocation across overdue penalties, interest, and principal.
  • Ledger: Enforces double-entry balance: \(\sum \text{Debits} == \sum \text{Credits}\) across all journal entries.
  • Audit trail: Captures before/after JSON diffs of every entity change.
  • Accruals: Calculates daily earned interest on an ACTUAL/365 day-count convention.
How to say this to the interviewer: "The app logic is divided into modular services. The schedule calculator handles amortization math, repayments manages waterfall collection, and the ledger service acts as the accounting guardian."
POINT 4

The Atomic Core: Prisma Interactive Transaction

This is the green container at the heart of the system. Every repayment executes as an atomic 5-step pipeline:
  1. Check key: Inspects the Idempotency-Key header. If already processed with an identical SHA-256 payload hash, returns cached HTTP 200 without touching the database again.
  2. Lock loan: Executes SELECT id FROM loans WHERE id = ? FOR UPDATE. This puts an exclusive database-level row lock on the loan record in MySQL InnoDB. Concurrent threads are forced to wait.
  3. Get balance: Dynamically sums all debits and credits from the ledger to compute the true outstanding balance under lock. Rejects overpayments with HTTP 400.
  4. Waterfall: Allocates incoming funds: overdue penalties first → due interest second → principal third.
  5. Post ledger: Creates balanced double-entry legs (e.g. Debit Cash ₹1,000 / Credit Principal ₹800 / Credit Interest ₹200).

Guaranteed invariant: Any failure at any step immediately rolls back the entire transaction. Zero half-baked state can ever persist.

How to say this to the interviewer: "This green box is where financial integrity is guaranteed. Inside a single Prisma transaction, we check idempotency, lock the loan row with SELECT FOR UPDATE to prevent race conditions, derive fresh balance under lock, execute the waterfall, and write balanced ledger entries. If anything fails, MySQL rolls back every single step."
POINT 5

MySQL 8 Storage & The Verification Loop

All changes commit to MySQL InnoDB across 5 normalized storage groups: Loan tables, Repayments + keys, Ledger, Audit log, and Accrual log.

At the bottom of the diagram is our Offline Verification Loop:
  • Data generator (seed 42): Deterministically created 5,000 synthetic events (valid payments, network retry keys, conflict keys, overpayments).
  • Replay engine: Hammered the live API with 8 concurrent workers at 179.4 req/s.
  • Verify ledger (9 checks): An automated audit script verified 9 mathematical invariants against MySQL.
  • Report files: Proved that Total Debits equal Total Credits with exactly 0 paise difference across ₹4.21 Crore of ledger entries.
How to say this to the interviewer: "Finally, everything is persisted to MySQL 8. To prove this architecture works under real production stress, we generated 5,000 synthetic events with seed 42, replayed them across 8 workers at 179 req/s with 0 server errors, and ran an automated verification script that confirmed a global trial balance difference of exactly 0 paise."

🎙️ The 2-Minute Interview Walkthrough Script

Practice reading this verbatim. It moves logically from top to bottom through the diagram in under 2 minutes:

"1. Where requests come from..."

"Looking at the top of the architecture diagram, requests enter from three sources: operational users like loan officers and managers via REST API, a scheduled midnight cron for daily interest accruals, and an 8-worker replay harness we built for load testing."

"2. The gateway security..."

"All HTTP traffic hits our Express API Gate. Here, JWT middleware validates the token, RBAC checks enforce Segregation of Duties—for example, preventing loan officers from approving loans—and our centralized error handler ensures clean, standardized error responses."

"3. The business modules..."

"Requests are then routed to their respective domain services: Loans manages schedules, Repayments manages payment collection, Ledger enforces double-entry rules, and Accruals calculates daily interest on an ACTUAL/365 basis."

"4. The atomic core (The most critical part)..."

"The centerpiece of the architecture is the green box: our atomic Prisma transaction. When a payment arrives, we first check the idempotency key using SHA-256 request hashing. We then place an exclusive row lock on the loan using MySQL's SELECT FOR UPDATE. Under this lock, we derive the remaining balance, run our waterfall allocation—penalties first, then interest, then principal—and post balanced debits and credits to the double-entry ledger. If any step fails, MySQL rolls back the entire transaction."

"5. Production verification..."

"Finally, at the bottom, we proved the correctness of this design by generating 5,000 synthetic events, replaying them with 8 workers at 179 requests per second with zero 500 errors, and verifying with our reconciliation script that our global trial balance had a net difference of exactly 0 paise."
